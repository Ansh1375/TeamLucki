## Summary:

The motivation for this project comes from the lasting question of the relationship between socioeconomic factors and public safety. While it is commonly believed that poverty drives crime, this project seeks to quantify the relationship within the city of Chicago. Our primary research question asks, to what extent does the poverty rate of a community area in Chicago correlate to its total reported crime count between 2020 and 2024? We chose Chicago because not only is it our home city, but it is also a large and diverse city that has historically been known to have a higher crime rate. It also contains many unique districts with their own demographics and cultures. By focusing on the period between 2020 and 2024, we are analyzing an important shift in urban history. This timeframe captures the immediate and long-term societal shifts following the COVID-19 pandemic, a time period where many cities across the country reported higher crime rates and economic stress. The world changed heavily due to COVID-19, and by using this time period, we can more accurately represent the current state of the world.

To answer this, we developed a data pipeline that integrates two distinct datasets: the City of Chicago's reported crime incidents and a socioeconomic dataset from Chicago containing income and poverty indicators. This project used a programmatic approach to data integration, ensuring that raw incident-level data could be accurately collected by community ID and merged with socioeconomic indicators. While these datasets contain vast amounts of information, they were not ready to be analyzed without any work being done on them. The crime dataset contains millions of rows and dozens of columns, with each row representing an individual incident with a time stamp and coordinate. Some of these rows were duplicates, and we had to ensure that the data was clean prior to working with it. In contrast, the socioeconomic dataset is aggregated by community area. This meant we had to bind the datasets despite the different specificities. We had to group the crime dataset by community_id to generate a crime count for each neighborhood. This data was then merged with the socioeconomic dataset, which contained the poverty rate and median income. We then had to clean the data by handling missing values and data type inconsistencies to ensure its accuracy. Finally, we automated this process by creating a run-all script. This script manages the execution flow and cleans and merges the data before visualization.

Our findings indicate a slight, but not statistically significant, positive correlation between poverty rates and crime density. The project successfully automated the transition from data acquisition to a final visualization, proving that the analysis can be repeated as new data comes to fray. By providing this framework, we hope to contribute a tool that allows for ongoing analysis into this question, and we hope to move the conversation from subjective evidence to data-driven insights.

## Data Profile:

This project uses two main datasets: a crime incident dataset from the City of Chicago Data Portal and a socioeconomic dataset from Chicago World Atlas. These datasets were chosen because they allow us to compare reported crime patterns across Chicago community areas with poverty and income indicators from those same areas. Since our main research question focuses on whether poverty rate is related to crime levels, both datasets needed to share a common geographic unit. In this project, that shared unit is the Chicago community area ID.

### Chicago Crime Dataset

The crime dataset comes from the City of Chicago Data Portal and contains reported crime incidents across the city. Each row in this dataset represents an individual crime report. The dataset includes incident-level information such as the date of the crime, block location, primary crime type, crime description, whether an arrest was made, whether the crime was domestic-related, police district, ward, community area, year, and location coordinates. The location column includes latitude and longitude information, which could be useful for mapping or spatial analysis, although our project mainly focused on community area trends.
This dataset is very large, so it could not be uploaded directly to GitHub. Instead, the project includes a script that downloads the crime data from a Box link and saves it locally as `crime.csv`. This allows the project to stay reproducible without storing a massive file in the repository. The crime data is used to calculate total reported crime counts by community area. After cleaning, the `Community Area` column is renamed to `community_id` so it can be merged with the socioeconomic dataset.

### Socioeconomic Dataset

The socioeconomic dataset comes from Chicago World Atlas and is stored in the project repository as `socioeconomic.csv`. This dataset is much smaller than the crime dataset because it is already aggregated at the community area level. Each row represents a Chicago community area, rather than an individual event. The dataset includes the community area name, GEOID/community area ID, median household income for 2020–2024, and poverty rate for 2020–2024.
The main columns used from this dataset are `GEOID`, `Name`, `INC_2020-2024`, and `POV_2020-2024`. `INC_2020-2024` represents median household income, while `POV_2020-2024` represents the percent of residents in families living below the Federal Poverty Level. These indicators come from the U.S. Census Bureau American Community Survey tables, which makes the dataset useful for measuring economic conditions across neighborhoods. In the cleaning process, `GEOID` is renamed to `community_id` and `Name` is renamed to `community_name` so the dataset can be merged more clearly with the crime data.

### Relationship Between the Datasets

The two datasets relate to each other through Chicago community areas. The crime data starts as incident-level data, meaning each row is one reported crime. The socioeconomic data starts as community-level data, meaning each row is one neighborhood/community area. To make the datasets comparable, the crime data is grouped by `community_id` to create a total crime count for each community area. This grouped crime table is then merged with the socioeconomic dataset using the shared `community_id` column.
This structure lets us compare the poverty rate and median income of each community area with the number of reported crimes in that same area. Because the datasets are organized at different levels at first, one important part of the project was transforming the crime data from individual reports into community-level summaries. Without that step, the two datasets could not be meaningfully compared.

### Ethical and Legal Considerations

There are also ethical concerns with using crime and socioeconomic data. Even though both datasets are publicly available, crime data can easily be misunderstood if it is used without context. Reported crime counts do not always represent the true amount of crime in an area, because reporting rates, policing patterns, community trust, and enforcement practices can vary across neighborhoods. This means the results should not be used to label certain communities as “bad” or to blame residents for crime levels.
The socioeconomic data also needs to be handled carefully because poverty and income are sensitive community-level indicators. In this project, we are not trying to stereotype neighborhoods or suggest that poverty directly causes crime. Instead, we are using the data to explore whether there is a measurable relationship between economic conditions and reported crime patterns in Chicago. The analysis should be understood as a starting point for data-driven discussion, not as a complete explanation of public safety or community conditions.
Legally, both datasets come from public data sources, so they can be used for educational and research purposes. However, the project avoids exposing unnecessary individual-level details beyond what is already publicly available. The final analysis focuses on aggregated community-level patterns rather than individual incidents.

## Data Quality

The data quality assessment focused on checking whether the crime and socioeconomic datasets were complete, consistent, and usable for answering our research question. Since our analysis depends on comparing crime counts and poverty rates by community area, the most important quality issue was making sure both datasets could be accurately linked using `community_id`.
One of the first issues we found was that some crime records were missing a valid `community_id`. This mattered because community area was the main geographic unit used in our analysis. If a crime record did not have a community ID, it could not be connected to a Chicago community area or matched with socioeconomic data. Because of this, those rows were removed from the merged dataset. This helped make sure that every remaining crime record could be tied to a specific community area.
A second issue appeared after the initial merge between the crime dataset and the socioeconomic dataset. The merged dataset had missing values in the socioeconomic columns, especially `community_name`, which showed that some crime records were not matching correctly. At first, this looked like a major data problem, but the issue was mainly caused by inconsistent data types. The `community_id` column was not stored the same way across both datasets, with one version being treated more like a numeric/float value and the other being treated differently. To fix this, we converted the `community_id` columns in both datasets to numeric values before merging. After this correction, the socioeconomic data matched properly, and the cleaned socioeconomic subset had no missing values in `community_id`, `community_name`, `INC_2020-2024`, or `POV_2020-2024`.
We also checked for duplicate crime records because duplicate incident rows could inflate the total crime counts for certain community areas. Since our final analysis depends on crime counts, duplicates would make the results less accurate. To address this, duplicate rows were removed using key identifying columns, including `Date`, `Block`, `Primary Type`, `Description`, and `community_id`. This allowed us to remove repeated entries while still keeping distinct crime incidents.
Another quality issue was the presence of missing values in the `Location` column. This column contains latitude and longitude information, but it was not central to our final research question. Since our analysis was based on community areas rather than exact coordinates, missing location values were not as important as missing community IDs. Because of this, the `Location` column was treated as less relevant for the final analysis and was not used as a main variable.
Overall, the cleaned merged dataset had 2,268,996 rows and 14 columns after removing unusable and duplicate records. It also included 77 unique community areas, which matches the expected number of Chicago community areas. This gave us confidence that the final dataset was organized at the correct geographic level and could be used to compare community-level crime counts with poverty and income indicators. Even though the data still has limitations, especially because reported crime data may reflect reporting and policing patterns, the cleaning process made the dataset consistent enough for our project’s analysis.

## Data Cleaning

The data cleaning process focused on making the crime and socioeconomic datasets usable together. Since the two datasets came from different sources and were organized differently, we had to clean the column names, standardize the merge key, remove unusable records, handle duplicates, and create a final merged dataset for analysis.
The first step was loading both datasets into Python using pandas. The crime dataset was loaded from `crime.csv`, while the socioeconomic dataset was loaded from `socioeconomic.csv`. Because the crime dataset was too large to store directly in GitHub, the project also includes a script that downloads it from the provided Box link if the file is not already available locally. This helped make the project reproducible while avoiding GitHub file size issues.
After loading the datasets, we stripped extra spaces from the column names in both files. This was a small but important step because hidden spaces in column names can cause errors when selecting, renaming, or merging columns. Cleaning the column names made the rest of the code more reliable.
Next, we renamed the key columns so the two datasets could be joined clearly. In the crime dataset, `Community Area` was renamed to `community_id`. In the socioeconomic dataset, `GEOID` was renamed to `community_id`, and `Name` was renamed to `community_name`. This made the shared geographic identifier consistent across both datasets and made the final merged dataset easier to understand.
We then converted `community_id` in both datasets to numeric values. This addressed one of the main merge issues we found during the quality assessment. Before this step, some values did not match correctly because the community ID columns were stored using different formats. By standardizing the data type, the merge was able to correctly connect crime records with their matching community-level socioeconomic information.
The socioeconomic dataset was also reduced to only the columns needed for this project: `community_id`, `community_name`, `INC_2020-2024`, and `POV_2020-2024`. This kept the merged dataset focused on the variables directly related to our research question. Median household income and poverty rate were the main socioeconomic indicators used to compare against crime patterns.
After preparing both datasets, we performed a left merge using `community_id`. This kept the crime records as the base dataset while adding community name, median income, and poverty rate information when a matching community ID was available. We then checked the shape of the merged data and counted missing values in `community_name` to see whether the merge worked correctly.
Rows with missing `community_id` values were removed because they could not be assigned to a community area. Since the project analyzes crime by community area, records without this information could not contribute to the final research question. Keeping them would have added noise without helping the analysis.
We also removed duplicate crime records. Duplicate rows can inflate crime counts and make some community areas appear to have more crime than they actually do. To address this, duplicates were identified using important incident-level columns such as `Date`, `Block`, `Primary Type`, `Description`, and `community_id`. Removing these repeated entries helped make the final crime counts more accurate.
Finally, we reviewed missing values and data types in the cleaned merged dataset. The `Location` column had missing values, but since the final analysis was based on community area rather than latitude and longitude, this column was not treated as essential. The cleaned dataset was saved as `crime_with_ses.csv`, which became the final merged file used for analysis and visualization.
Overall, each cleaning step was done to make the data more consistent, reduce unnecessary errors, and prepare the files for a fair comparison between reported crime counts and socioeconomic conditions across Chicago community areas.

## Findings

The main finding from this project is that the relationship between socioeconomic status and reported crime in Chicago is present, but not as simple or strong as we originally expected. Since our main question was focused on poverty and crime, we looked at scatterplots, grouped boxplots, a correlation heatmap, outlier checks, and a basic linear regression model.
The poverty rate scatterplot showed a slight upward pattern between poverty rate and total crime count. In other words, some communities with higher poverty rates also had higher crime counts. However, this trend was not strong across all communities. The regression results showed an R-squared value of `0.0241`, meaning poverty rate only explained about 2.4% of the variation in crime count. The p-value was `0.1773`, which means the relationship was not statistically significant at the usual 0.05 level. Based on this, we cannot confidently say that poverty rate alone predicts crime count in Chicago community areas.
The correlation heatmap supported this same idea. The correlation between poverty rate and crime count was `0.16`, which is positive but weak. Median household income had a correlation of `-0.03` with crime count, meaning income had almost no linear relationship with crime count in this dataset. However, income and poverty were strongly negatively correlated at `-0.81`, which makes sense because communities with higher median income generally had lower poverty rates.
The visualizations also showed that crime counts varied heavily across community areas. The top 10 communities by crime count were Austin, Near North Side, Near West Side, Loop, South Shore, North Lawndale, West Town, Humboldt Park, Auburn Gresham, and Greater Grand Crossing. Austin had the highest total crime count with `122,185` reported crimes. Other high-crime areas included Near North Side with `100,342`, Near West Side with `84,820`, and Loop with `78,993`. These were also identified as statistical outliers using a crime z-score greater than 2.
One important finding is that high-crime communities were not all economically similar. For example, Austin had a lower median household income of about `$51,827`, while Near North Side, Near West Side, and Loop all had median household incomes above `$116,000`. This shows why the relationship between poverty and crime is more complicated than just saying poorer communities have more crime. Some higher-income areas may have higher crime counts because they are dense, commercial, tourist-heavy, or downtown areas with more daily activity.
The boxplots gave a slightly clearer group-level pattern. Communities in the high-poverty group tended to have higher median crime counts than low-poverty and middle-poverty communities. Similarly, low-income communities had a higher median crime count than middle-income communities. However, the high-income group also had several major outliers, which shows that income alone does not explain crime patterns either.
Finally, the crime type composition chart showed that common crime categories in the top 10 communities included theft, battery, assault, criminal damage, motor vehicle theft, deceptive practice, narcotics, and other offenses. Theft appeared especially large in downtown or higher-income areas like the Loop and Near North Side, while battery and assault were more visible across several lower-income communities. Overall, the results suggest that poverty may be one part of the story, but crime patterns are also shaped by population density, neighborhood activity, policing/reporting differences, and the types of places located within each community.

## Future Work

One of the main lessons learned from this project is that working with real public datasets is usually more complicated than it looks at first. The crime dataset was very large, while the socioeconomic dataset was much smaller and already summarized by community area. Because of this, a major part of the project was not just analyzing the data, but making sure the two datasets could actually work together. We had to clean column names, standardize community IDs, remove unusable rows, check for duplicates, and make sure the merge was accurate. This showed us that data curation is one of the most important parts of a project like this because even a simple analysis can become misleading if the datasets are not prepared correctly.
Another lesson learned is that correlation does not always match expectations. Going into the project, we expected poverty rate to have a clearer relationship with crime count. Instead, the results showed only a weak positive correlation between poverty and crime, and the regression model was not statistically significant. This does not mean poverty is unrelated to crime, but it does show that poverty alone is not enough to explain reported crime patterns across Chicago. Some high-income communities, such as the Loop and Near North Side, also had high crime counts, likely because of factors like population density, tourism, business activity, and the number of people moving through those areas each day.
For future work, one major improvement would be to include population-adjusted crime rates instead of only raw crime counts. Raw crime counts can be misleading because communities with more residents, more visitors, or more commercial activity may naturally have more reported incidents. A crime rate per 1,000 residents would make the comparison between communities more fair. It would also be useful to include daytime population or foot traffic data for areas like the Loop, since downtown communities may have high crime counts even if their residential population is not very large.
Another future improvement would be adding more socioeconomic variables. This project mainly focused on poverty rate and median household income, but crime patterns may also relate to unemployment, education level, housing instability, age distribution, population density, and access to public services. Adding more variables could give a more complete view of community conditions and make the analysis less dependent on one or two indicators.
Future work could also examine changes over time. Instead of grouping all crime data together, we could compare crime trends year by year from 2020 to 2024. This would help show whether certain communities improved, worsened, or stayed stable over time. It could also help connect crime patterns to major events such as the COVID-19 pandemic, economic changes, or policy changes in the city.
Finally, future work could include more detailed spatial analysis and better visualizations. Since the crime dataset includes location information, mapping crime patterns across Chicago could make the results easier to understand. A community area map, heatmap, or interactive dashboard would help users visually compare poverty, income, and crime levels across the city. Overall, this project created a useful starting point, but future versions could improve the analysis by using adjusted crime rates, more variables, time-based trends, and stronger geographic visualization.

## Challenges

One of the main challenges in this project was working with the size of the Chicago crime dataset. The file was too large to upload directly to GitHub, so we had to find a different way to make the project reproducible. To solve this, we uploaded the crime dataset to Box and included a script that downloads the file locally if it is not already present. This made the workflow more realistic, but it also added an extra step because the analysis depends on the data being downloaded correctly before the rest of the project can run.
Another challenge was merging two datasets that were organized at different levels. The crime dataset was incident-level, meaning each row represented one reported crime. The socioeconomic dataset was community-level, meaning each row represented one Chicago community area. Because of this, we could not directly compare the datasets without first transforming the crime data into community-level summaries. We had to group the crime records by `community_id` and calculate total crime counts before comparing them with poverty and income values.
We also ran into issues with the merge itself. At one point, the merged dataset had many missing socioeconomic values, which made it look like the community areas were not matching correctly. After checking the data more closely, we realized the issue came from inconsistent data types in the `community_id` column. Once we converted the community ID fields to the same numeric format, the merge worked more accurately. This was a useful reminder that even when two columns look like they contain the same values, they may not join correctly if they are stored differently.
Duplicate and missing records were another challenge. Some crime records were missing community IDs, which meant they could not be used for our community-area analysis. We also found duplicate crime entries that could have inflated the final crime counts. These issues required extra cleaning steps before the analysis could be trusted.
A final challenge was interpreting the results carefully. We expected poverty and crime to have a stronger relationship, but the actual results showed only a weak positive correlation and a non-significant regression result. This made the findings more nuanced. Instead of forcing the data to match our original expectation, we had to explain that crime patterns are affected by many factors beyond poverty, including population density, downtown activity, reporting differences, and policing patterns.
Overall, the biggest challenge was not just running the code, but making sure the data was clean, the merge was accurate, and the results were interpreted responsibly. This project showed us that data analysis is not only about producing visuals or statistics, but also about understanding what the data can and cannot tell us.

## Reproducing:

To reproduce this analysis, follow the steps below.
1. Prerequisites
    Ensure you have Python 3.12.2 or later and the pip package manager installed on your system
2. Environment Setup
    Install the necessary software dependencies using the provided requirements.txt and/or environment_dump.txt files. You can run pip install -r requirements.txt.
3. Data Acquisition
    Ensure that the crime.csv (Incident-level data from the Chicago Data Portal) and ses_data.csv (Socioeconomic indicators data from the Chicago Health Atlas) are installed. 
    Note: The crime.csv file is very large, so install it from the provided Box link.
4. Execute the Workflow
    The entire analysis is executed via a single run_all.py script
5. Verification
    Upon successful completion, the script will output the crime_with_ses.csv and poverty_correlation.png artifacts into the project folder.
